## 0. How to use this document

This is the single source of truth for how we review code in UmerOS. Use it two ways:

1. **Author self-check** — before opening a PR, walk Section 4 and confirm every applicable item is satisfied.
2. **Reviewer checklist** — during review, work top-to-bottom; every 🔴 must be resolved before approval, 🟡 should be resolved or explicitly waived by a maintainer, 💭 are discretionary.

The standard is grounded in (a) the **design intent** expressed across the `MainTask/prompt` and `MainTask/Raw Data` sources, and (b) the **actual state of the repo** (studied 2026-08-20): ~735 active Python modules, a zero-trust `security/` subsystem, 921 passing unittest tests, and an existing `.github/workflows/security_scan.yml`. Where the repo already has a good convention, we *codify* it. Where we found real gaps or design/code drift, we *enforce* them below.

### 1.1 Language & tech-stack policy (decided 2026-08-20)

Enforced per the user's directive *"write code only in Python … front end in Flutter"* — **now DECIDED (Flutter wins over the prior Kivy call):**

- **Backend = Python only.** All OS logic, services, AI, drivers, and kernel glue are **Python ≥ 3.12**. No other backend language is permitted (C/ASM only for the bootloader entry / HW interrupt table / context-switch stub, behind a `ctypes` binding). Flag any new backend module not in Python.
- **Frontend = Flutter (Dart) — DECIDED.** This overrides the earlier *Kivy canonical* decision (H11). Flutter UIs are written in **Dart**, not Java — correct the instruction's wording. Java (or Kotlin) is used only for *native platform-channel* code on Android, never the app logic. The repo currently has **no Flutter/Dart source** and is Kivy-based in `README.md`/`setup.py`, so this is a **migration**: drop `kivy` from `requirements.txt` (H15), plan the Flutter frontend, and treat existing Kivy references as legacy drift to refresh (like H14).
- **Reviewer action:** new backend code must be Python; the **canonical frontend lives in `ui/flutter_ui/` (Dart)** — all new UX work goes there. Any `*.java` in the frontend is flagged unless it is native Android platform-channel code; flag any *new* Python/Tkinter/Kivy UI in `ui/*.py` as legacy (retire/migrate to Flutter, H25); and **every frontend PR must satisfy the HCI checklist (§4.8)** — Human-Computer Interaction principles are a frontend design mandate.

**Tier-labeling is MANDATORY (design rule, non-negotiable).** Every module/feature is labelled `[TODAY]` ✅ / `[EXPERIMENTAL]` 🔬 / `[FUTURE]` 🔮. *Unlabelled features are rejected at review.* Consequence: a PR that adds behavior without a tier label is a 🔴.

**Command-interface contract (dominant pattern — enforce consistently):**
Every shell command implements `execute(self, args=None) -> int` (returns a POSIX-style exit code), exposes `self.name`, `self.description`, `self.usage`, supports `--help`/`--version`, and ships a `_selftest()`. The base class `core/command.py` currently declares `execute(self, *args) -> Any` with `name/description/category/privileges` — **known mismatch** (Hotspot H6). New code follows the `args=None -> int` convention; converge `core/command.py` to it.

## 2. Principles

1. **Review teaches, it doesn't gatekeep.** Every comment explains *why* and offers a concrete fix.
2. **Trust the zero-trust model.** UmerOS assumes no process is trusted. PRs that execute untrusted input, shell out to the host, or weaken capability checks get the hardest scrutiny.
3. **Microkernel boundaries are contracts.** Kernel core handles *only* IPC, scheduling, memory mapping, capability enforcement. Everything else is a user-space Python service; a crash there must not panic the kernel. Review for privilege creep.
4. **Small, focused PRs review better.** Aim for one logical change per PR; keep diffs reviewable (<~400 lines ideal).
5. **Automate the boring parts.** Formatting, linting, static security, and type-checking run in CI so humans focus on logic and design.
6. **Tests are part of the change, not an add-on.** No test = no merge for anything behavioral.
7. **Green is not optional.** The full suite (currently 921) must pass with zero regressions; new modules add their own `_selftest()` + suite tests.
8. **No impossible claims.** Code/comments must not assert capabilities the hardware can't deliver. Use "simulated" / "quantum-inspired" / "EXPERIMENTAL" where no QPU/NPU exists. "Zero-error qubits" is FUTURE-only.

## 3. Severity model

| Marker | Meaning | Merge impact |
|---|---|---|
| 🔴 **Blocker** | Correctness bug, security vulnerability, data loss, broken contract, missing critical error handling, or **violation of a design mandate** (tier label, zero-trust, legal/privacy) | **Must be fixed** before approval |
| 🟡 **Suggestion** | Real improvement: missing validation, confusing logic, missing test, perf issue, duplication, convention drift | Fix or get explicit maintainer waiver |
| 💭 **Nit** | Style/naming/doc nicety; low risk | Author's discretion |

## 4. The review checklist

Work this list for every PR. Items marked **[UmerOS]** are project-specific and derived from the design sources and the codebase study.

### 4.1 Correctness 🔴/🟡
- [ ] **Does it do what the PR claims?** Read the description, then verify the code path actually implements it.
- [ ] **Return contracts honored.** Commands return `int` (exit code); async kernel APIs are `await`ed; `MemoryManager.free` raises on double-free; `CapabilityManager.query` never raises. Flag deviations.
- [ ] **No silent fallthrough.** `execute()` handles `--help`/`--version` and returns non-zero on bad/missing args (per `test_bin.py` expectations).
- [ ] **Off-by-one / boundary checks** on indexes, slices, qubit counts, memory pages (page-aligned to 4096).
- [ ] **[UmerOS] Quantum qubit sizing** — never hardcode qubit counts; use `_required_qubits(circuit_ops)` (past critical bug).
- [ ] **[UmerOS] Stale exports** — `__init__.py` files re-export only symbols that exist (past break: `MicrocodeVendor` vs `CPUVendor`). Grep imports vs definitions.
- [ ] **[UmerOS] Microkernel boundary** — no filesystem/network/driver logic sneaks into the privileged core; new work belongs in a user-space service.

### 4.2 Security 🔴 (highest weight for this project)
- [ ] **No `eval`/`exec` on untrusted input.** 🔴 `initrd/ai_helper.py:166` does `eval(line)` on a history file (marked `# noqa: S307`); must-fix — parse instead of eval, or gate behind a capability + signed history.
- [ ] **No command injection via `subprocess`.** 🔴 `bin/user_commands.py:_exec_command` runs `[sh, "-c", command]` as another user — confirm `command` is not attacker-controlled and `shell=False` semantics hold. 🟡 `bin/boolean_ops.py:411` and `etc/issue_motd.py` shell out to the host; prefer arg lists (no `shell=True`).
- [ ] **No hardcoded secrets.** 🔴 `lib/security.py:72` `PASSWORD = "password"` default; 🟡 `scripts/test_endpoint.py` `secret="test-secret"`, `usr/misc_data_manager.py` `BIRTHTOKEN="birthtoken"`. Use `os.urandom(32)` / env vars / secret store.
- [ ] **[UmerOS] Exposed credential remediation.** 🔴 `settings.local.json` contains a **live OpenRouter key** (`sk-or-v1-…`). Revoke+rotate it, add to `.gitignore`, and purge from git history before any merge touches it.
- [ ] **[UmerOS] Zero-trust enforcement (design mandate).** New syscalls/IPC/fs/network ops must go through `CapabilityManager`/`SecuritySandbox`; IPC messages HMAC-signed & replay-protected; every process verified at creation (code-signing). Bypassing = 🔴.
- [ ] **[UmerOS] Crypto standards (design mandate).** PQC via `liboqs` (Kyber/Kyber ML-KEM, Dilithium ML-DSA); hashing SHA3-512; symmetric AES-256-GCM; TLS post-quantum 1.3. No home-grown crypto.
- [ ] **[UmerOS] AI self-healing is gated.** The design allows the AI to generate & deploy hot-patches and roll back on regression. Any such path is 🔴-review: generated code must be **capability-scoped, sandbox-executed, logged to an audit trail, and rollback-tested** before auto-apply; never apply untrusted LLM output to a privileged path.
- [ ] **[UmerOS] Self-healing patch is never executed.** `umer_ai.py:SelfHealingEngine.generate_patch` returns *code strings* (TODAY: comment-only stubs — safe). Any FUTURE path that `exec`/`eval`s a generated patch must satisfy the H12 gate (capability scope + sandbox + audit + rollback). The standalone `ai/self_healing.py:SelfHealingService.mitigate` "restarts process in isolated state" with **no sandbox/audit/rollback** — must be brought under the H12 gate before any auto-recovery (Hotspot H21).
- [ ] **[UmerOS] Package integrity.** `umer-pkg` artifacts (`.umerpkg`) must be cryptographically signed; installs verify signatures (chain-of-trust). Review any change to the package/签名 flow as security-critical.
- [ ] **[UmerOS] Installer legal mandate.** Every installer action must be preceded by the EULA/"I AGREE" check (design non-negotiable). PRs touching `installer/` must preserve this; no silent install.
- [ ] **[UmerOS] Boot-path integrity is fail-closed.** The kernel hash check (`boot/bootloader.py:verify_kernel`) and EFI binary trust (`boot/efi_system.py:is_binary_trusted`) must **reject** unknown/missing/forbidden binaries — never return `True` permissively (Hotspots H27/H28, extends H17). The "I AGREE" liability waiver must not be auto-accepted (H29).
- [ ] **[UmerOS] OTA/update integrity is fail-closed.** The over-the-air update path (`cloud/ota_updater/update_system.py`) must **verify the publisher's signature before applying** any payload — never apply an unsigned/unverified update. `verify_and_apply` currently returns `True` and applies even when no crypto engine is present (and, when present, self-signs the payload instead of verifying the manifest signature) — a fail-open supply-chain gap (Hotspot H46, same class as H17/H27/H28, breaks the signed-`.umerpkg` mandate, §4.2). Any missing/invalid signature must **abort** the update; wire it to the real `CryptoEngine`/`Dilithium` `verify()` path in `security/`.
- [ ] **[UmerOS] Compatibility-launched foreign binaries are sandboxed + capability-gated.** `compatibility/container_engine.py` launches Linux ELF / Windows `.exe` (Wine) / Android APK (ADB) via `subprocess.Popen` (arg-list, **no `shell=True` — good**) but **unsandboxed** (no chroot/namespace/resource quotas) and inherits the full env; `compatibility/container.py:ZeroTrustContainer.execute_binary` calls `capabilities.check(...)` but only *prints* a message and still runs the binary — a **fail-open** zero-trust gate (Hotspot H51, same class as H17/H27/H28/H46). Before promotion to `[TODAY]`, wrap every launch in an isolated namespace + drop capabilities + gate under `CapabilityManager`; **never ignore a failed capability check**.
- [ ] **Deserialization.** No `pickle.loads`/`yaml.load`/`marshal` on untrusted bytes (keep it that way).
- [ ] **Bandit clean.** New code must not introduce Bandit findings above the agreed baseline (Section 7).

### 4.3 Privacy & AI governance 🔴/🟡
- [ ] **[UmerOS] Opt-in only.** AI training / cloud offload / telemetry require explicit per-session user consent; no personal data leaves the device without permission (design mandate). Flag any default-on data egress.
- [ ] **[UmerOS] Consent & erasure.** Consent logged; `right to erasure` (`umer-privacy clear-all`) supported; anonymise before any sync (GDPR/ISO alignment).
- [ ] **[UmerOS] Local-first.** Inference runs on-device; cloud delegation explicit + consented. Review network calls from `ai/` for silent exfiltration.
- [ ] **[UmerOS] AI egress consent (🔴).** `ai/umer_ai.py:LocalAIAssistant.query` must call `AIGovernance.check_consent("online_ai")` (or equivalent, logged) **before** delegating to `OnlineProvider` (which POSTs the user prompt to an external API endpoint). The module's own privacy guarantee — *"NO user data leaves the device by default"* — is broken if prompts leave without explicit, recorded consent. Flag any `ai/` path that sends user text off-device without a consent gate (Hotspot H18).

### 4.4 Maintainability 🟡/💭
- [ ] **[UmerOS] Tier label present** on the module (`[TODAY]`/`[EXPERIMENTAL]`/`[FUTURE]`) and on each non-obvious feature (design rule: unlabelled = rejected).
- [ ] **[UmerOS] `boot/` tier labels (H31):** only `bootloader.py` carries a `[TODAY]` label; add one to every other `boot/` module. `boot/init.py` also skips the per-file baseline (no `from __future__ import annotations`, no `logging`, no docstrings) and must be brought up to standard (H32).
- [ ] **[UmerOS] Per-file baseline (design mandate):** every file includes `try/except` error handling, `logging` calls, **Python type hints**, and **Google-style docstrings**. Missing any = 🟡.
- [ ] **Public functions have type hints.** `from __future__ import annotations` at top.
- [ ] **[UmerOS] Command-interface consistency** — commands match `execute(args=None)->int` (POSIX exit code) + `self.name/description/usage` + `_selftest()` (see H6). **Root cause:** the base class `core/command.py:30` still declares `execute(self, *args) -> Any`, which is why 27/44 `bin/` modules inherit the wrong signature (H35/H55) — fix the base class first, then the subclasses. Also enforce the declared `privileges` in the base `execute()` (Hotspot H56); do not let `su`/`login`/root commands run without a capability check (§4.2).
- [ ] **Specific exceptions, not bare `except`.** 🟡 ~30+ broad `except Exception`/`except:` in `bin/` mask real errors; catch the specific type and log.
- [ ] **Naming & clarity.** Classes `CapWords`, functions `snake_case`, constants `UPPER`. Self-documenting names over comments.
- [ ] **No dead/commented code** left in (e.g. the commented `exec(chat_code, …)` in `kernel/umer_kernel.py:1717` — track it in an issue, don't leave it inline).
- [ ] **Duplication** extracted into shared helpers (esp. repeated FHS path logic across `bin/`/`usr/`/`lib/`).
- [ ] **[UmerOS] Logging vs print** — error/diagnostic output uses `loguru`/`logging`, not `print`, except interactive shell stdout where print is acceptable.
- [ ] **[UmerOS] Realism labels** — comments don't claim QPU/fault-tolerant behavior that doesn't exist; mark `# TODO: QPU integration` on future hooks.
- [ ] **[UmerOS] `ai/` per-file baseline + tier labels.** `ai/assistant.py` and `ai/self_healing.py` currently violate the baseline (no type hints, no docstrings, no `logging`, **no tier label**, use `print()`). `ai/providers.py` and `ai/resource_predictor.py` lack `[TODAY]/[EXPERIMENTAL]/[FUTURE]` labels on their classes. Every `ai/` module must carry tier labels + the full baseline before approval (Hotspot H19).
- [ ] **[UmerOS] No duplicated AI stacks.** `ai/` ships parallel implementations: `assistant.py:AIAssistant` ≈ `umer_ai.py:LocalAIAssistant`; `self_healing.py:SelfHealingService` ≈ `umer_ai.py:SelfHealingEngine`; `resource_predictor.py:ResourcePredictor` ≈ `umer_ai.py:AIResourceManager` (both EWMA + z-score spike detection, *different* `SPIKE_Z_THRESHOLD`: 2.0 vs 2.5). Consolidate into `umer_ai.py`; delete or clearly mark the standalone stubs `EXPERIMENTAL`/legacy (Hotspot H19).
- [ ] **[UmerOS] `bin/` study notes (v1.7).** `bin/` = ~44 FHS `/bin` + `/usr/*` command modules (≈19k LOC). (a) **0/44** carry a tier label — every command file violates the mandatory label rule (H40); (b) **27/44** use the wrong `def execute(self, *args)` signature instead of `def execute(self, args=None) -> int` (H35/H6) — only 12 modules use the correct form; (c) `su` (`user_commands.py`) spawns `[sh,"-c",command]` **as another user** and its `_exec_shell` is a stub that `return 0` (H36/H4); (d) `LoginCommand` `-f`/`-F` sets `skip_auth=True`, bypassing password auth (H37 🔴); (e) `ChageCommand` is defined twice (`usr_cmds.py:3045`, `usr_commands.py:1938`) (H38); (f) ~30+ broad `except` mask real errors (H8/H39). Subprocess usage is otherwise safe: arg-list + `timeout`, no `shell=True`, and no `eval`/`os.system`/`pickle`/`yaml.load` anywhere in `bin/`.
- [ ] **[UmerOS] `dev/` study notes (v1.12).** `dev/` = ~43 FHS `/dev` **virtual device-node filesystem** modules (≈6,800 LOC): a central `DeviceManager`/`DeviceNode`/`DeviceType` (`dev/core.py`) registry plus ~40 pseudo-device / subsystem / command modules (null/zero/random/full/tty/ptmx, input, shm, net/tun, fuse, memory `/dev/mem`+`/dev/kmem`+`/dev/port`, SCSI, NVMe, KVM, dri, snd, and the `udevadm`/`losetup`/`makedev`/`mknod` commands). Overall the **cleanest folder security-wise**: **no** `eval`/`exec`/`os.system`/`subprocess`/`shell=True`/`pickle`/`yaml.load`/`ctypes` anywhere, and licensing is **clean GPLv3** (headers say `Licence: GPLv3`; zero Apache-2.0 strays — a good counterexample to `boot/`). But: (a) 💭 **0/43** files carry a tier label (H58 — violates §4.4); (b) 🟡 the base `DeviceNode` defaults to `mode=0o666` (world-writable) and a long list of nodes are explicitly `0o666` (`null`/`zero`/`full`/`tty`/`ptmx`/`shm`/`tun`/`fuse`/`i2c`/misc-char/misc-system…) — only the security-sensitive memory devices correctly use `0o640` (H59); (c) 🟡 `DeviceManager.sync_to_filesystem()` (`dev/core.py:211`) calls `os.mknod`/`os.mkfifo`/`os.symlink_to` to materialize **real** device nodes into the VFS **without a capability/privilege gate** — on a real `/dev` with host privileges this creates device special files (incl. world-writable ones from the `0o666` default), a zero-trust gap (H60, same "privileged op / no gate" family as H27/H28/H46/H51); (d) 💭 the `DeviceManager` singleton registry (`self._nodes`) has **no lock** — concurrent registration/hotplug could race (H61). `memory_devices.py` is the model to copy: `STRICT_DEVMEM` restricts `/dev/mem` to `ALLOWED_RANGES`, `/dev/kmem` is `AVAILABLE=False` (returns zeros), and access checks log warnings before denying.

### 4.5 Performance 🟡
- [ ] **No N+1 / repeated work** in loops (e.g. IPC send-in-loop, fs lookups).
- [ ] **Compression tests use compressible data** (`b"Umer OS test pattern " * N`), never `os.urandom()` — LZMA on random data times out (per dev guide).
- [ ] **Async correctness** — `await` coroutines; no blocking calls on the event loop; `sched.stop()` awaited in teardown; `asyncio.Lock` guards shared queues (per scheduler design).
- [ ] **No unbounded growth** — caches/maps bounded or sized.

### 4.6 Testing 🔴/🟡
- [ ] **Behavioral change has tests.** New command → add to its suite + a `_selftest()` entry; new kernel/security/quantum module → suite tests (see `tests/` mappings).
- [ ] **Tests are hermetic & fast** — no real network/host dependence unless explicitly a container/integration test; skip (don't hang) on missing platform (pattern from `liboqs/test_leaks.py`).
- [ ] **Assert the contract** — return codes, raises, HMAC verify, capability allow/deny, signature check — not just "runs without error."
- [ ] **No regressions** — full suite green (921) before merge.
- [ ] **Flaky-test check** — tests don't depend on wall-clock, ordering, or global state.

### 4.8 Frontend — Flutter/Dart & HCI principles 🟡

The frontend lives in **`ui/flutter_ui/`** and is written in **Dart** (Flutter). It must follow established **Human-Computer Interaction (HCI)** principles as a design mandate (the user explicitly requires HCI adherence). The current UI already does well: Material 3 theming (light/dark), `tooltip:` on icon buttons (a11y), keyboard shortcuts (Ctrl+K search, Esc to dismiss), a responsive windowing model (drag/resize/snap), notifications, and a spotlight search — good visibility, flexibility, and recognition-over-recall. Review new frontend PRs against these heuristics:

- [ ] **[HCI] Visibility of system status.** Show loading/working states; confirm async actions (OTA, package install, network calls) where they happen; surface errors in-context. (Nielsen #1)
- [ ] **[HCI] Match the real world / plain language.** Avoid OS-internal jargon in user-facing labels — e.g. "CPUIdle & Governor" / "Power & Idle" are developer terms; prefer "Power & Performance". (Nielsen #2)
- [ ] **[HCI] User control & freedom.** Every destructive or mode-changing action has an undo/escape path: window close/min/max are present; destructive ops (file delete, package remove) must confirm or be reversible. (Nielsen #3)
- [ ] **[HCI] Consistency & standards.** Use Material 3 components consistently; **do not duplicate the app registry** — `desktop_shell.dart` hardcodes the same app list in `_DesktopGrid`, `_GlobalSearchModal`, and `_LaunchPad` (DRY/consistency risk, Hotspot H23). Centralise it in one model. (Nielsen #4)
- [ ] **[HCI] Error prevention.** Confirm before destructive actions; validate inputs (e.g. the Control Center custom-wallpaper path field). (Nielsen #5)
- [ ] **[HCI] Recognition over recall.** Keep LaunchPad, Dock, and spotlight search; don't force GUI users to memorise commands. (Nielsen #6)
- [ ] **[HCI] Flexibility & efficiency.** Preserve keyboard shortcuts + draggable/resizable windows; expose accelerators for power users. (Nielsen #7)
- [ ] **[HCI] Aesthetic & minimalist.** M3 already applied; avoid clutter, keep one primary action per surface. (Nielsen #8)
- [ ] **[HCI] Help & documentation.** GUI surfaces self-explanatory; keep the About/Help entry and add first-run hints. (Nielsen #10)
- [ ] **[HCI] Accessibility (a11y).** Add `Semantics` labels for screen readers on custom widgets (dock, draggable windows, launchpad); ensure colour contrast in both themes; respect `uiScale`/`enableGlassmorphism`. Test with `find.bySemanticsLabel`, not just a mount smoke test (Hotspot H26). (Nielsen #9 + WCAG 2.1 AA)
- [ ] **[UmerOS] Frontend is Dart-only.** No Python/Kivy/Tkinter in the UX path. Legacy `ui/*.py` (Tkinter/CLI) is a retired headless fallback only (H25). Native Android platform code, if any, is Kotlin/Java (not the app logic).
- [ ] **[UmerOS] Frontend egress respects privacy.** The Dart UI uses `http` + `webview_flutter_windows` (browser/network apps) — any call sending user data off-device must pass the same opt-in consent gate as the backend (`AIGovernance`, §4.3 / H18).

### 4.9 Build & release integrity 🟡

`build/` is the **PyInstaller output** for the `UmerOS-GUI` freeze. Of its 16 files (~42 MB), only **2 are authored**: `build/UmerOS-GUI.spec` (PyInstaller spec) and `build/__init__.py` (empty package marker). Everything under `build/UmerOS-GUI/` — `*.toc`, `PYZ-00.pyz`, `UmerOS-GUI.pkg`, `base_library.zip`, `localpycs/*.pyc`, `warn-*.txt`, `xref-*.html` — is **generated** and correctly **out of review scope** per §0 (generated `.pyz`/`.exe` artifacts). The reviewable surface is the `.spec`. Build/release PRs must satisfy:

- [ ] **[UmerOS] Build targets the canonical frontend.** `build/UmerOS-GUI.spec:5` freezes `ui/umeros_gui.py` — the **legacy Tkinter GUI that H25 already retired** as superseded by Flutter (`ui/flutter_ui/`). Shipping this binary ships the wrong (superseded) frontend. Repoint the build at the canonical frontend before any release; don't distribute the retired Tkinter app as "UmerOS" (Hotspot H41).
- [ ] **[UmerOS] Frozen artifacts are signed.** `build/UmerOS-GUI.spec:36` sets `codesign_identity=None` — the distributable is **unsigned**, which breaks the zero-trust signed-artifact mandate (§4.2, signed `.umerpkg`, H17/H27/H28). Sign the frozen binary + `.pkg` before distribution; reconsider `upx=True` (L29), which packs/obscures the payload and trips AV (Hotspot H42).
- [ ] **[UmerOS] Build is reproducible / portable.** The spec hardcodes an absolute Windows path `F:\Pension Person Details\UmerOS\ui\umeros_gui.py` (L5) — machine-specific, breaks in CI/other dev machines. Derive the entry from the repo root so the build runs anywhere (Hotspot H43).
- [ ] **[UmerOS] Complete, optimized freeze.** `datas=[]`/`binaries=[]`/`hiddenimports=[]`/`excludes=[]` and `optimize=0` (L8-15) declare no assets/runtime deps and ship unoptimized bytecode — risk of missing data files / Tk runtime on a clean machine. Declare needed `datas`/`binaries`/`hiddenimports`, set `optimize>=1`, and verify the frozen app runs from a clean VM (Hotspot H44).
- [ ] **[UmerOS] Build is codified.** The build is invoked ad-hoc (`pyinstaller UmerOS-GUI.spec`); there is **no `Makefile`/`build.py`/CI build step** in-repo (extends H16 — no CI test step either). Codify the build + a signed-artifact release job so it is reproducible and auditable (Hotspot H44).
- [ ] **[UmerOS] Spec carries a license/tier label.** `build/UmerOS-GUI.spec` has no license header or `[TODAY]/[EXPERIMENTAL]/[FUTURE]` label (extends H7/H30/H40); `build/__init__.py` is a harmless 0-byte marker. Add a header to the spec for consistency (Hotspot H45).

## 5. The review process (workflow)

```
 Author dev → self-check (§4) → open PR → CI gates (§7) → ≥1 reviewer →
 resolve 🔴, waive 🟡 (maintainer) → approval → squash-merge to main →
 post-merge: confirm green, update docs
```

1. **Author self-check.** Run §4 against the diff locally. Run `ruff`, `bandit -c pyproject.toml`, `mypy`, and the relevant `tests/` suite.
2. **Open PR.** Target `main`. Fill the PR template (Section 10). Link issue. Keep it focused. Mark the PR's own tier.
3. **CI gates block merge** until green (lint, type, security baseline, full test suite, coverage floor).
4. **Assign reviewer(s).** At least one human reviewer; security-sensitive PRs (auth, IPC, crypto, `subprocess`, `eval`, self-healing/auto-patch, package signing, installer) require a **security reviewer** sign-off.
5. **Review round.** Use 🔴/🟡/💭 inline. One complete pass, not drip-fed. Ask when intent is unclear rather than assuming wrong.
6. **Address.** Author fixes 🔴, responds to each 🟡 (fix or justify). Re-request review.
7. **Approve & merge.** Maintainer merges (squash) only when §8 criteria are met.
8. **Post-merge.** Verify CI on `main` is green; update `docs/`/README test counts if they changed.

**SLA (suggested):** author responds within 2 business days; reviewer first pass within 2 business days.

- **Pre-commit:** `.pre-commit-config.yaml` running Ruff + gitleaks + trailing-whitespace/EOF on every local commit.

> Keep CI fast: run lint+type+unit in parallel; reserve Trivy/ZAP for `main`/release, not every PR.

- **`core/` study (v1.11):** `core/` = just 2 files — `core/command.py` (32 LOC, the **base `Command` class every `bin/` command inherits**) + `core/__init__.py` (1 line). It is the **root cause of the H6 contract drift**: `command.py:30` declares `execute(self, *args: Any) -> Any` (returns `Any`), so the 27/44 `bin/` modules using `def execute(self, *args)` are merely inheriting the wrong base signature (H35). Findings: 🟡 H55 fix the base class to `execute(args=None) -> int` to resolve H35 at the source; 🟡 H56 the base `Command` declares a `privileges: List[str]` field but **never enforces** it — zero-trust commands must gate execution on declared privileges via `CapabilityManager` (cf. - **`dev/` study (v1.12):** `dev/` = ~43 FHS `/dev` **virtual device-node filesystem** modules (≈6,800 LOC): a central `DeviceManager`/`DeviceNode`/`DeviceType` (`dev/core.py`) registry plus ~40 pseudo-device / subsystem / command modules (null/zero/random/full/tty/ptmx, input, shm, net/tun, fuse, memory `/dev/mem`+`/dev/kmem`+`/dev/port`, SCSI, NVMe, KVM, dri, snd, and `udevadm`/`losetup`/`makedev`/`mknod` commands). **Cleanest folder security-wise so far**: no `eval`/`exec`/`os.system`/`subprocess`/`shell=True`/`pickle`/`yaml.load`/`ctypes` anywhere, and licensing is **clean GPLv3** (headers say `Licence: GPLv3` — zero Apache-2.0 strays, a good counterexample to `boot/`).
