## H241 (session 227) — `app_name` unvalidated in `BuildTool` — RESOLVED

**Premise true for the path, but the row's severity note understated it — and it
hid a functional bug.**

The VFS does not confine on its own: `fs/vfs.py::_resolve` treats `..` as a
literal child name and `fs/qfs.py::write_file` keys its index by the raw path
string. So `scaffold('../../evil')` created directories literally named `..`
under `/sdk/projects` and index keys that no longer mean what they say. The row
is right that there is no *real* filesystem escape (QFS is an in-memory CAS
index), so the namespace damage is VFS-scoped.

But the same unvalidated name is also interpolated **unquoted into generated
Python**:

```python
class {app_name}(UmerApp):
    def __init__(self):
        super().__init__("{app_name}", "1.0.0")
```

Measured before the fix: **4 of 4 plausible names** (`my-app`, `1Bad`, `a b`,
`Evil"App`) produced a `src/main.py` that would not even `compile()`. `my-app`
is a perfectly ordinary app name. That is a functional bug, not just a security
one, and the row never mentions the code-generation half.

**Remedy: adopted the row's charset, rejected its exception.** `^[A-Za-z0-9_-]`
makes `..` and absolute paths *unrepresentable* rather than merely rejected. But
the refusal raises `core.path_guard.PathTraversalError` — the repo's canonical
CWE-22 type, imported with the same `try/except` idiom as `home/*` — instead of
inventing a new exception, so callers keep one security-refusal contract.

`safe_child`/`safe_join` were deliberately **not** used: they resolve through
`pathlib.Path.resolve()` against the *real* filesystem, which is wrong for a
logical VFS path (`safe_child(Path("/sdk/projects"), "X")` would resolve to
`F:\sdk\projects\X`). The logical analogue is a `posixpath.normpath`
containment assert, which `project_path()` performs after validation.

**New helpers:** `validate_app_name()`, `project_path()` (used by *both*
`scaffold` and `package`, assigned before the `if self.vfs:` branch so nothing is
written on refusal), `class_identifier()` (`my-app`→`my_app`, `1Bad`→`_1Bad`,
`class`→`class_app`) and `_py_literal()` (`json.dumps`) for the code sink.

`custom_app_code` is still written verbatim on purpose — that is H242's row, and
`test_custom_app_code_is_still_written_verbatim` pins the boundary so the two
items stay separable.

**Verification:** `tests/test_sdk_build_tool_h241.py` — **76 passed**. 14
traversal/separator/dot/whitespace/overlong/non-str names refused by both
methods; the decisive `test_nothing_is_written_on_refusal` uses a recording VFS
and asserts `calls == []`; accepted names all `compile()`; AST proof that both
methods *call* `project_path` and do so **before** the VFS branch; no
`f"/sdk/projects/{` left in the source; manifest/archive derivation; dry-run;
and the H240 header surviving the rewrite.

**Six mutations, all caught:** path inlined in both methods, path inlined in
`package` only, regex relaxed to admit `/.`, raw name in the generated class,
naive quoting in the code sink, and validation moved *after* the VFS writes.
One mutant first reported as "missed" was an invalid mutation of mine (it
inserted a `pass` instead of moving the call); rebuilt properly it is caught by
five tests.

**Regression:** 6014 testcases, 0 errors, 95 skipped, 5 failed (the known
`test_legal_pii_h137` set). The +76 delta is exactly the new file; diffed the
two JUnit runs — nothing added elsewhere, nothing lost. `sdk/` still scans 7/7.

## H242 (session 228) — `custom_app_code` written verbatim — RESOLVED

**Premise true; line numbers stale** (`:33-47` → `:142-171`, because H241 rewrote
the file).

The row offers two options: *"document it as trusted-developer input, **or**
restrict it"*. Both were done, in the right proportion — the second one on its
own would break a legitimate use.

**Documented.** `scaffold`'s docstring now states that `custom_app_code` is
trusted developer input, that it is *not* sandboxed, and that it must never be
fed from an untrusted source because the written file is imported by the
packaging flow.

**Screened, not restricted.** New `validate_custom_code()` refuses exactly three
things:

1. a non-string;
2. a control character — Unicode `Cc` other than `\n`/`\r`/`\t`; NUL, ESC, DEL
   and C1 are never intentional in source and corrupt the written file;
3. source that does not `compile()`.

The parse check is the high-value half: today a typo silently produced a project
that could never import.

**What it deliberately does NOT do:** block a fragment. A partial file is a
legitimate thing to scaffold, and the row's "require a `UmerApp` subclass"
suggestion would reject it. So `sdk/validator.py::AppValidator.validate_code` is
reused as the authority and its findings are printed as `[SDK] Warning:` lines
while the write proceeds. `AppValidator` is *imported*, not re-defined — pinned
by an identity assertion — so there is one definition of "valid app code" rather
than two that could drift apart.

Validation runs **before** the `if self.vfs:` branch, the same discipline as
H241, so a refusal leaves the VFS untouched.

**Verification:** `tests/test_sdk_custom_code_h242.py` — **26 passed**. Five
control characters refused by both the helper and `scaffold` with nothing

## H247 (session 230) — 🟡 `security/security.py` `IPCAuthenticator`: anti-replay claimed, not implemented

**Drift-recon: the premise is TRUE, and it hid a second lie.**

Replay really was possible. The live class at `:156` held no nonce or timestamp
state at all; the only anti-replay implementation in the file was **commented
out** (L285–334). But that dead code is a *different API* — `sign_message`
returns a **dict** (adding `timestamp`/`nonce`/`mac`) and `verify_message` takes
**one** argument. Re-enabling it verbatim would have broken:

* `docs/developer_guide.md:226-228` — `mac = auth.sign_message({...})`;
  `auth.verify_message({...}, mac)`;
* `ui/umeros_gui.py:380` — constructs `IPCAuthenticator()` and discards the sig;
* `tests/test_security.py::TestIPCAuthenticator` — pins `sign_message -> str`
  **and determinism** (`test_sign_deterministic`: same message + same key ⇒ same
  MAC). A fresh nonce inside the message makes that impossible.

The second lie the row never mentions: the class docstring claimed
**HMAC-SHA3-512** while the code hashes with `hashlib.sha3_256`. The module
docstring claimed "SHA3-512" at L35 *and* plain "HMAC-SHA256" at L21 — both
wrong — and `ui/umeros_gui.py:1567` repeated the 512 claim in the GUI.

**Remedy — replay defence in the verifier, so the wire format survives.**

`verify_message` now remembers every MAC it accepts for `replay_window`
(300 s default) and refuses a second presentation. `_prune` bounds the cache by
TTL **and** a hard `max_entries` cap, dropping the oldest half under a flood (a
documented bounded-memory fallback, not silent exhaustion).

The ordering is the security-critical part: the MAC is compared **before**
anything is remembered. Record first and an attacker floods *distinct* forged
MACs until the cap evicts genuine entries — re-enabling replay of exactly those.
My first draft of this test only re-sent one forged MAC 20 times, which cannot
evict anything (a forged MAC is a distinct string, so it never collides). The
rewritten `test_forged_macs_cannot_evict_genuine_ones_from_the_cache` floods 64
distinct MACs against a `max_entries=8` cache, and the mutant that inverts the
order now fails it.

`sign_envelope`/`verify_envelope` are the **opt-in** path for callers needing
defence that survives a restart or holds across receiver instances: the envelope
binds `timestamp`, `nonce` and `ttl` into the signed bytes, rejects stale *and*
future-stamped envelopes (a bad sender clock must not buy an unbounded validity
period), never mutates the caller's dict, and is **total** — malformed input
returns `False` instead of raising, because envelopes arrive from untrusted
peers. `replay_window=0` restores purely stateless verification.

Both verify paths keep `hmac.compare_digest`. The SHA3-512 claims are corrected
to SHA3-256 in the module docstring, the class docstring and the GUI.

**Tests:** `tests/test_ipc_replay_h247.py` — 29 passed, 15 subtests. The
decisive one is
`test_the_replay_is_refused_because_of_state_not_because_the_mac_broke`: it
proves the MAC is *still* exactly what was signed (`sig == auth._mac(msg)`) and
that a fresh instance accepts it, so the rejection is genuinely anti-replay and
not a broken MAC — and it states the per-instance boundary honestly. Plus the
unchanged public API (64-char hex, determinism, the `developer_guide` snippet
verbatim, tamper ⇒ False) and four claim-vs-code checks.

**Nine mutations, all caught:** replay check removed, compare/remember order
inverted, `rotate_key` keeping the cache, future-timestamp check dropped, stale
check dropped, envelope replay check removed, the SHA3-512 docstring lie
restored, memory cap disabled, expiry disabled. Each mutant asserted to *differ*
from the original, and the file restored byte-identically (sha256 verified).

**Regression:** 6125 testcases, 0 errors, 95 skipped, 6 failed — the 5 known
