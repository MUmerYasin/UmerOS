## boot/ folder study (v1.6 of the standard)
- User directed study of `boot/` (20 .py modules ~9.8k LOC + 1 C stub `uefi_stub.c` + `boot_samples/` fixtures: config/System.map/vmlinuz-6.1.0-umeros binary).
- **Scope:** `boot/` is a `/boot` **management toolkit** for a Linux-hosted boot env (FHS 3.0 audit, GRUB2, systemd-boot/BLS, EFI+Secure Boot, UKI, bzImage header parser, kernel cmdline+sysctl, CPU microcode, boot splash/framebuffer, kdump crash kernel, initrd). It is NOT the UmerOS microkernel entry — that's `kernel/umer_kernel.py` (imported by `bootloader.py`/`init.py`). Consistent with "runs atop an existing kernel (Linux userspace)".
- Overall quality is HIGH: 19/20 files have `from __future__ import annotations`, type hints, Google docstrings, `_selftest()`; `subprocess` calls are all arg-list + `timeout` (no `shell=True`).
- **🔴 H27:** `bootloader.py:147` `verify_kernel` returns `True` on missing image ("Permissive during prototype phase") + when `expected_hash is None` → fail-open kernel integrity (same class as H17).
- **🔴 H28:** `efi_system.py:524-533` `is_binary_trusted` returns `True` for `DISABLED`/`SETUP_MODE` and never consults `dbx` → fail-open Secure Boot (extends H17).
- **🟡→🔴 H29:** `init.py:27` auto-accepts the "I AGREE" liability waiver in non-interactive mode → bypasses §4.2 installer EULA mandate.
- **🟡 H30:** 10 `boot/` files declare `Licence: Apache 2.0` headers (extends H7/H20). **🟡 H31:** only `bootloader.py` has a tier label (19/20 missing). **🟡 H32:** `uefi_stub.c` is a 33-line `printf` placeholder, no real UEFI/ctypes binding (despite `init.py:33` claiming ctypes sim). **🟡 H33:** hash inconsistency (SHA3-256 kernel vs SHA-256 EFI vs mandated SHA3-512). **🟡 H34:** `boot/` CLI skips `core/command` contract; `demo_boot.py` uses unprefixed sibling imports; `init.py` skips per-file baseline.
- Standard bumped to **v1.6**: §1 status → +`boot/`; §4.2 added fail-closed boot-path integrity item (H27/H28/H29); §4.4 added `boot/` tier-label + `init.py` baseline note (H31/H32); §9 added **H27–H34**; §11 quick-ref added `boot/` study line.

## dev/ folder study (v1.12 of the standard)
- User directed study of `dev/` (43 `.py` modules ≈6,800 LOC) — a virtual FHS `/dev` **device-node filesystem**: central `DeviceManager`/`DeviceNode`/`DeviceType` (`dev/core.py`, 245 LOC) registry + ~40 pseudo-device / subsystem / command modules (null/zero/random/full/tty/ptmx, input, shm, net/tun, fuse, memory `/dev/mem`+`/dev/kmem`+`/dev/port`, SCSI, NVMe, KVM, dri, snd, udevadm/losetup/makedev/mknod commands).

- **💭 H58:** **0/43** files carry a tier label (same gap as `bin/` 0/44, `boot/` 19/20).

- **🟡 H60:** `DeviceManager.sync_to_filesystem()` (dev/core.py:211) calls `os.mknod`/`os.mkfifo`/`os.symlink_to` to materialize **real** device nodes into the VFS with **no capability/privilege gate** — on a real `/dev` with host privileges this creates device special files (incl. world-writable from `0o666`), incl. `/dev/mem`/`/dev/kmem`/`/dev/port`. - `memory_devices.py` is the model to copy: `STRICT_DEVMEM` restricts `/dev/mem` to `ALLOWED_RANGES`, `/dev/kmem` `AVAILABLE=False` (returns zeros), `_check_access` logs warnings before denying.
